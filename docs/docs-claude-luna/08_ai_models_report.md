# Отчёт о работе приложения с AI-моделями

> **Состояние отчёта:** соответствует исходному коду проекта на 16 августа 2026 года.
> Отчёт разделяет фактически реализованные возможности и варианты дальнейшего расширения.

## 1. Краткое резюме

AI Chatbot Assistant — монолитное SSR-приложение на FastAPI с браузерным интерфейсом чата. Для генерации ответов приложение использует официальный Python SDK `openai` в асинхронном режиме (`AsyncOpenAI`), но отправляет запросы не в OpenAI напрямую, а в OpenAI-совместимый API **GitHub Models**.

Фактическая цепочка обработки сообщения:

```text
Браузер
  → POST /api/chat с JSON {"prompt": "..."}
  → FastAPI и проверка cookie-аутентификации
  → app.services.chat.get_chat_response()
  → AsyncOpenAI.chat.completions.create()
  → GitHub Models API
  → ответ модели
  → JSON {"response": "..."}
  → браузер
```

В текущей версии реализован один независимый вызов LLM на каждый запрос. История диалога, streaming, выбор модели пользователем, tool calling и мультиагентный оркестратор отсутствуют.

## 2. Текущий AI-стек

| Компонент | Реализация |
|---|---|
| Язык | Python 3.13 |
| Web-фреймворк | FastAPI, async handlers |
| SDK | `openai` (`AsyncOpenAI`) |
| Провайдер | GitHub Models API |
| Base URL | `https://models.github.ai/inference/` |
| Модель в коде | `openai/gpt-4o` |
| Секрет доступа | `GITHUB_TOKEN` из `.env` или окружения |
| Протокол | HTTP JSON, OpenAI Chat Completions-compatible |
| Ответ | обычный полный JSON-ответ, без SSE/WebSocket |
| Контекст | только текущий prompt; история не сохраняется |

Клиент создаётся один раз при импорте модуля `app/services/chat.py`:

```python
from openai import AsyncOpenAI

from app.core.config import settings

client = AsyncOpenAI(
    api_key=settings.GITHUB_TOKEN,
    base_url="https://models.github.ai/inference/",
)
```

Модель и URL сейчас зашиты в исходный код. Настройки `LLM_MODEL`, `LLM_BASE_URL` и `LLM_TIMEOUT` в конфигурации проекта пока отсутствуют.

## 3. Как выполняется запрос к модели

### 3.1. Вход пользователя

Фронтенд отправляет запрос на защищённый endpoint:

```http
POST /api/chat
Content-Type: application/json
Cookie: fastapiusersauth=<jwt>
```

Тело запроса валидируется схемой `ChatRequest`:

```json
{
  "prompt": "Объясни, что такое FastAPI"
}
```

Схема содержит одно обязательное поле:

```python
from pydantic import BaseModel


class ChatRequest(BaseModel):
    prompt: str
```

### 3.2. Авторизация и маршрутизация

`app/api/v1/chat.py` объявляет `POST /chat`; роутер подключается в `app/main.py` с prefix `/api`, поэтому внешний путь — `/api/chat`.

До вызова модели FastAPI разрешает зависимость `current_user`. JWT извлекается из cookie `fastapiusersauth`, после чего FastAPI-Users проверяет пользователя. Без действительной аутентификации запрос завершается ответом `401 Unauthorized`.

Фактический endpoint:

```python
@router.post("/chat")
async def chat_endpoint(
    prompt: ChatRequest = Body(...),
    user: User = Depends(current_user),
):
    response = await get_chat_response(prompt=prompt.prompt)
    return {"response": response}
```

Переменная `user` подтверждает авторизацию, но в AI-запрос не передаётся.

### 3.3. Формирование сообщения и вызов GitHub Models

Текущая бизнес-логика находится в `app/services/chat.py`:

```python
async def get_chat_response(prompt: str) -> str:
    message = (
        "Hey ChatGPT, you are a AI chatbot don not tell your name or any personal information. "
        "Here is the prompt you asked for: "
        + prompt
    )
    response = await client.chat.completions.create(
        model="openai/gpt-4o",
        messages=[{"role": "user", "content": message}],
    )
    return response.choices[0].message.content.strip() if response.choices else ""
```

Особенности реализации:

1. Системная инструкция и пользовательский текст объединяются в одну строку.
2. В API передаётся только сообщение с ролью `user`; отдельное сообщение `system` не используется.
3. Запрос асинхронный, поэтому event loop FastAPI не блокируется ожиданием сетевого ответа.
4. `stream` не включён: сначала генерируется весь ответ, затем он возвращается клиенту.
5. Извлекается текст из `response.choices[0].message.content`.

### 3.4. Ответ браузеру

При успешной генерации endpoint возвращает:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "response": "FastAPI — асинхронный веб-фреймворк для Python..."
}
```

JavaScript фронтенда удаляет индикатор набора и отображает `data.response` в окне чата.

## 4. Возможности текущего приложения

### Реализовано

- регистрация пользователя;
- вход через cookie-аутентификацию;
- дополнительный JWT backend для API-клиентов;
- защищённая страница чата;
- отправка текстового prompt в AI-модель;
- получение текстового ответа;
- асинхронное обращение к внешнему LLM API;
- базовая обработка сетевой ошибки на стороне браузера;
- Swagger-документация FastAPI на `/docs`.

### Не реализовано

- сохранение conversations и messages;
- передача предыдущих сообщений в следующий запрос;
- выбор модели, температуры и других параметров через API или UI;
- streaming через SSE или WebSocket;
- загрузка файлов и мультимодальные сообщения;
- function calling / tool use;
- RAG, embeddings и поиск по документам;
- автоматические retries, timeout и circuit breaker для LLM;
- квоты и rate limiting на пользователя;
- оценка качества, moderation и журналирование AI-запросов;
- мультиагентное выполнение.

## 5. В каком виде происходит общение с нейросетью

Обмен состоит из двух HTTP-границ.

### Граница 1: браузер — FastAPI

Это JSON API приложения:

```json
{
  "prompt": "Напиши краткое резюме текста"
}
```

Ответ:

```json
{
  "response": "..."
}
```

Браузер дополнительно отправляет cookie с JWT. API не принимает в текущей схеме массив сообщений, роль, настройки генерации или ID разговора.

### Граница 2: FastAPI — GitHub Models

SDK формирует OpenAI-совместимый запрос примерно такого вида:

```json
{
  "model": "openai/gpt-4o",
  "messages": [
    {
      "role": "user",
      "content": "Hey ChatGPT, ... пользовательский текст ..."
    }
  ]
}
```

GitHub Models возвращает объект Chat Completions с массивом `choices`; сервис берёт текст первого выбора. Сырые метаданные ответа, usage, finish reason и идентификатор запроса наружу не передаются.

## 6. Модели и провайдеры

### 6.1. Что реально используется сейчас

В текущем коде фактически поддерживается одна комбинация:

- **провайдер:** GitHub Models API;
- **модель:** `openai/gpt-4o`;
- **клиент:** `AsyncOpenAI`;
- **токен:** `GITHUB_TOKEN`;
- **режим:** Chat Completions без streaming.

Это не означает, что каталог GitHub Models ограничен одной моделью. Это означает, что приложение не предоставляет механизм выбора другой модели: идентификатор модели зашит в `app/services/chat.py`.

### 6.2. Какие модели можно подключить после параметризации

GitHub Models публикует динамический каталог моделей. Через тот же сервис можно использовать любую модель, которая одновременно:

1. доступна конкретному GitHub-аккаунту и токену;
2. разрешена для GitHub Models API;
3. поддерживает используемый endpoint Chat Completions;
4. принимает передаваемый формат `messages`;
5. имеет правильный идентификатор модели.

В каталогах GitHub Models в разные периоды встречаются модели OpenAI, Meta Llama, Microsoft Phi, Mistral, DeepSeek и другие. Их точный список, лимиты и доступность меняются, поэтому перед настройкой нужно сверяться с актуальным каталогом GitHub Models, а не считать приведённые семейства гарантированно доступными.

Пример требуемого изменения при выборе другой модели:

```python
MODEL = "<идентификатор-модели-из-каталога-github-models>"

response = await client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": message}],
)
```

### 6.3. Другие провайдеры

`AsyncOpenAI` работает с провайдерами, предоставляющими OpenAI-совместимый API. Теоретически приложение можно адаптировать к следующим классам поставщиков:

| Провайдер или класс | Совместимость с текущим кодом | Что потребуется |
|---|---|---|
| GitHub Models | Да, фактически используется | Только `GITHUB_TOKEN` |
| OpenAI API | Протокол совместим, но не настроен | Изменить `base_url`, ключ и model ID |
| Azure OpenAI | Требуется отдельная схема endpoint/API version | Изменить клиент и конфигурацию |
| Локальный Ollama/vLLM | Возможна OpenAI-совместимость | Локальный `base_url`, модель и отсутствие внешнего ключа |
| Другие OpenAI-compatible gateway | Обычно возможно | Проверить формат endpoint, auth и поддерживаемые параметры |
| Anthropic API | Не является прямой заменой | Использовать Anthropic SDK или отдельный адаптер |

Важное ограничение: в текущем приложении `base_url` и модель не вынесены в настройки. Поэтому перечисленные варианты **не подключаются одной переменной окружения** — сначала нужен небольшой рефакторинг сервиса и конфигурации.

## 7. Возможно ли мультиагентное использование

### Текущее состояние

Нет. Сейчас есть один вызов одной модели на один пользовательский prompt. В коде отсутствуют:

- роли и специализированные агенты;
- очередь или оркестратор задач;
- вызов инструментов;
- общий state между шагами;
- передача результата одного агента другому;
- финальный агент-синтезатор;
- лимиты итераций, бюджета и времени.

Сам факт использования OpenAI-compatible API не делает приложение мультиагентным.

### Возможная архитектура расширения

Мультиагентный режим можно реализовать поверх текущего сервиса:

```text
Пользователь
  → API /api/agent-task
  → Оркестратор
      ├─ Агент-аналитик: разбивает задачу
      ├─ Агент-исследователь: собирает факты/вызывает tools
      ├─ Агент-критик: проверяет результат
      └─ Агент-синтезатор: формирует финальный ответ
  → JSON или streaming-ответ
```

Минимальные компоненты:

1. `AgentDefinition`: имя, system prompt, модель и разрешённые tools.
2. `AgentOrchestrator`: последовательный или параллельный запуск агентов.
3. `AgentState`: задача, промежуточные результаты, лимит шагов и итог.
4. хранилище задач и сообщений, если выполнение должно переживать HTTP-запрос;
5. таймауты, retries, rate limiting и аудит каждого вызова;
6. политика разрешений для инструментов и проверка недоверенного вывода.

Для независимых подзадач можно использовать `asyncio.gather`, но параллельность должна быть ограничена semaphore и квотами провайдера. Для зависимых шагов нужен последовательный workflow. Мультиагентность увеличивает стоимость, задержку и поверхность prompt injection, поэтому для обычного вопроса предпочтительнее один вызов.

## 8. Ограничения и риски текущей AI-интеграции

### Надёжность

- нет timeout на вызов GitHub Models;
- нет `try/except` для `RateLimitError`, `APITimeoutError`, `APIConnectionError` и других ошибок SDK;
- ошибка провайдера может превратиться в HTTP 500;
- нет retry с backoff;
- нет лимита размера prompt;
- пустой `GITHUB_TOKEN` разрешён конфигурацией и обнаруживается только при запросе.

### Безопасность

- пользовательский текст напрямую конкатенируется с инструкцией, что повышает риск prompt injection;
- дефолтный `SECRET` небезопасен для реального развёртывания;
- AI-ответ и пользовательский текст отображаются через `innerHTML` в шаблоне чата — необходима безопасная вставка через `textContent` или проверенный sanitizer;
- нет rate limiting, поэтому один пользователь может инициировать много внешних LLM-вызовов;
- prompt и ответы не имеют политики удаления/маскирования чувствительных данных.

### Продуктовые ограничения

- модель не знает предыдущих сообщений;
- нельзя выбрать другой провайдер без изменения исходников;
- нельзя получить частичный ответ во время генерации;
- нет метрик токенов, стоимости и latency;
- нет тестов с mock-моделью.

## 9. Рекомендуемая последовательность улучшений

1. Исправить запуск: создать `app/static/` или монтировать каталог условно.
2. Сделать `SECRET` обязательным и валидировать `GITHUB_TOKEN`.
3. Вынести в настройки `LLM_BASE_URL`, `LLM_MODEL`, `LLM_TIMEOUT`, system prompt и лимит prompt.
4. Добавить timeout, обработку ошибок SDK, retry/backoff и единый формат ошибок API.
5. Заменить `innerHTML` безопасным рендерингом.
6. Добавить тесты endpoint с замоканным `AsyncOpenAI`.
7. Добавить `Conversation` и `Message`, затем передавать ограниченную историю в `messages`.
8. Добавить SSE streaming после определения контракта фронтенда.
9. Только затем внедрять tools или мультиагентный оркестратор с лимитами и аудитом.
