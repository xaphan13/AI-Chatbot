# 08 — Отчёт по работе приложения с AI-моделями

> Отчёт описывает фактическую реализацию на момент анализа. Возможности, помеченные
> как «перспектива», в кодовой базе ещё не реализованы.

---

## 1. Назначение AI-части приложения

**AI Chatbot Assistant** предоставляет аутентифицированному пользователю веб-интерфейс
для однократных текстовых запросов к большой языковой модели (LLM). Браузер передаёт
сообщение серверу, сервер обращается к модели через GitHub Models API и возвращает
готовый текстовый ответ.

Текущая реализация — простой stateless-чат:

- история переписки не сохраняется;
- модель не получает предыдущие сообщения;
- ответ возвращается только после завершения генерации;
- нет вызовов инструментов, поиска в сети, работы с файлами или базы знаний;
- нет агентов и оркестрации нескольких моделей.

## 2. Используемая модель и провайдер

| Параметр | Текущее значение |
|---|---|
| Провайдер AI-инференса | GitHub Models API |
| Endpoint | `https://models.github.ai/inference/` |
| SDK | `openai` (`AsyncOpenAI`) |
| Модель | `openai/gpt-4o` |
| Авторизация | Bearer-токен из `GITHUB_TOKEN` |
| Режим вызова | Асинхронный `chat.completions.create(...)` |
| Формат результата | Один готовый JSON-ответ, без streaming |

Конфигурация токена определена в `app/core/config.py`:

```python
class Setting(BaseSettings):
    GITHUB_TOKEN: str = ""
```

Клиент и модель определены в `app/services/chat.py`:

```python
from openai import AsyncOpenAI

from app.core.config import settings

client = AsyncOpenAI(
    api_key=settings.GITHUB_TOKEN,
    base_url="https://models.github.ai/inference/",
)
```

> `GITHUB_TOKEN` должен быть задан в `.env` или переменных окружения. В текущем коде
> пустое значение не проверяется при старте приложения: ошибка авторизации проявится
> только при первом обращении к чату.

## 3. Как выполняется AI-запрос

### 3.1. Сквозной поток

```text
Пользователь в браузере
    │
    │ POST /api/chat
    │ {"prompt": "Объясни принцип работы FastAPI"}
    ▼
FastAPI: app/api/v1/chat.py
    │ Проверка JWT/cookie и DTO ChatRequest
    ▼
Сервис: app/services/chat.py
    │ Формирует сообщение и вызывает AsyncOpenAI
    ▼
GitHub Models API
    │ Генерирует завершение чата моделью openai/gpt-4o
    ▼
FastAPI
    │ {"response": "...готовый ответ модели..."}
    ▼
Браузер отображает ответ в интерфейсе чата
```

Маршрут чата требует аутентифицированного пользователя, однако сам объект `user` пока
не влияет на содержимое запроса к модели:

```python
@router.post("/chat")
async def chat_endpoint(prompt: ChatRequest = Body(...), user: User = Depends(current_user)):
    response = await get_chat_response(prompt=prompt.prompt)
    return {"response": response}
```

### 3.2. Формирование запроса к модели

Сервис соединяет инструкцию и пользовательский текст в одну строку, затем отправляет
её как единственное сообщение с ролью `user`:

```python
async def get_chat_response(prompt: str) -> str:
    message = (
        "Hey ChatGPT, you are a AI chatbot don not tell your name or any personal information. Here is the prompt you asked for: "
        + prompt
    )
    response = await client.chat.completions.create(
        model="openai/gpt-4o",
        messages=[{"role": "user", "content": message}],
    )
    return response.choices[0].message.content.strip() if response.choices else ""
```

Фактически используется OpenAI-совместимый Chat Completions API. Инструкция не
передаётся в отдельном сообщении `role="system"`, а история `messages` не накапливается.
Поэтому для модели каждый запрос — новая, независимая задача.

## 4. В каком виде происходит общение с нейросетью

### Между браузером и приложением

Обмен выполняется по HTTP в формате JSON. Клиентский JavaScript отправляет:

```javascript
const response = await fetch('/api/chat', {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',
    },
    body: JSON.stringify({ prompt: message })
});

const data = await response.json();
addMessage(data.response, 'ai');
```

Контракт API:

```json
POST /api/chat
Content-Type: application/json

{
  "prompt": "Сформулируй краткое резюме текста"
}
```

```json
HTTP/1.1 200 OK
Content-Type: application/json

{
  "response": "Конечный текстовый ответ модели"
}
```

Для доступа к маршруту браузер автоматически отправляет HttpOnly-cookie
`fastapiusersauth` с JWT. В теле API передаётся только пользовательский `prompt`.

### Между приложением и AI-провайдером

Библиотека `openai` создаёт HTTP-запрос к OpenAI-совместимому endpoint GitHub Models.
Семантически он содержит модель и массив сообщений:

```json
{
  "model": "openai/gpt-4o",
  "messages": [
    {
      "role": "user",
      "content": "<инструкция приложения> <текст пользователя>"
    }
  ]
}
```

Ответ SDK содержит список `choices`; приложение читает первый элемент:

```python
response.choices[0].message.content
```

Ни SSE, ни WebSocket, ни потоковая передача токенов не применяются. Пользователь видит
индикатор набора текста, но получает результат целиком, после завершения внешнего
вызова.

## 5. Возможности приложения

### Реализовано

- Регистрация, вход и выход пользователей через FastAPI-Users.
- Защищённый интерфейс чата, доступный только после аутентификации.
- Отправка произвольного текста в LLM и отображение текстового ответа.
- Асинхронный серверный вызов AI через GitHub Models API.
- Индикатор ожидания ответа и автоматическая прокрутка сообщений на клиенте.
- Обработка истёкшей сессии в UI: при `401` пользователь перенаправляется на `/login`.

### Не реализовано

- Память диалога, история сообщений и список бесед.
- Streaming ответов и постепенная отрисовка токенов.
- Выбор модели, температуры, лимитов токенов и системного промпта пользователем или
  через настройки.
- Таймауты, повторные попытки, нормализованная обработка ошибок и лимиты запросов.
- RAG: поиск по документам, векторная БД, цитирование источников.
- Function calling / tool calling: выполнение действий модели через API приложения.
- Голос, изображения, вложения и мультимодальные запросы.
- Оценка качества ответов, аудит запросов, метрики стоимости и трассировка.

## 6. Мультиагентное использование

**В текущем приложении мультиагентный режим отсутствует.** Есть единственный вызов
одной модели `openai/gpt-4o` на один пользовательский запрос. В коде нет понятий
`agent`, маршрутизатора задач, общей памяти, делегирования или обмена сообщениями
между агентами.

Технически расширение возможно, но требует отдельной архитектуры, а не только замены
строки с моделью. Минимальная схема может выглядеть так:

```text
Пользовательский запрос
    │
    ▼
Оркестратор
    ├── классифицирует задачу и выбирает исполнителей
    ├── передаёт им ограниченный контекст
    ├── контролирует число вызовов, время и стоимость
    ▼
Специализированные агенты
    ├── исследователь — собирает факты из разрешённых источников
    ├── аналитик — сопоставляет и проверяет данные
    └── редактор — формирует единый ответ
    ▼
Оркестратор проверяет и возвращает итог пользователю
```

Для практической реализации понадобятся:

1. **Оркестратор** — сервис, который определяет порядок вызовов и агрегирует результат.
2. **Явные роли и промпты** — отдельные инструкции и разрешённые инструменты для каждого
   агента.
3. **Состояние** — таблицы бесед/сообщений или другое хранилище контекста, изолированное
   по пользователям и задачам.
4. **Инструменты** — строго ограниченные функции для поиска, БД или внутренних API;
   нельзя предоставлять модели неограниченный доступ к системе.
5. **Надёжность и контроль затрат** — timeout, лимиты параллелизма, budget на задачу,
   логирование цепочки вызовов и обработка частичных сбоев.
6. **Проверка качества** — валидация результатов, защита от prompt injection и правила
   обработки недостоверных ответов.

Для текущего MVP более рациональный следующий шаг — сначала добавить сохранение
диалогов, обработку ошибок и streaming. Мультиагентность оправдана только для задач,
где разделение ролей действительно улучшает качество результата.

## 7. Какие модели и провайдеры можно использовать

### Используется сейчас

Сейчас код работает только со следующей парой:

| Провайдер | Модель | Статус |
|---|---|---|
| GitHub Models API | `openai/gpt-4o` | Используется в коде |

### Возможные варианты интеграции

Клиент `AsyncOpenAI` поддерживает OpenAI-совместимые API. Поэтому после вынесения
`base_url`, ключа и имени модели в конфигурацию можно подключать провайдеров, которые
предоставляют совместимый Chat Completions endpoint:

| Тип провайдера | Условие подключения |
|---|---|
| GitHub Models | Выбрать доступную в аккаунте GitHub модель и указать её точный идентификатор. |
| OpenAI | Использовать стандартный OpenAI endpoint и отдельный API-ключ. |
| Другой OpenAI-совместимый сервис | Проверить совместимость Chat Completions API, схему аутентификации, допустимые имена моделей и лимиты. |
| Локальный сервер модели | Развернуть сервер с OpenAI-совместимым API, настроить локальный `base_url`, аутентификацию и ресурсы инфраструктуры. |

Это **не означает**, что перечисленные провайдеры уже поддерживаются приложением:
сейчас `base_url` и модель захардкожены в `app/services/chat.py`. Чтобы сделать выбор
без изменения кода, необходимо как минимум добавить настройки вида:

```python
class Setting(BaseSettings):
    LLM_API_KEY: str
    LLM_BASE_URL: str
    LLM_MODEL: str = "openai/gpt-4o"
    LLM_TIMEOUT_SECONDS: float = 30.0
```

Затем нужно создавать `AsyncOpenAI` с этими параметрами и тестировать каждый провайдер
отдельно. Доступный набор моделей, цены, квоты, поддержка инструментов и мультимодальных
данных определяются конкретным провайдером и его тарифом, а не SDK `openai`.

## 8. Технические ограничения и риски

При развитии AI-части следует учитывать следующие особенности реализации:

- Модель, endpoint и системная инструкция жёстко заданы в коде.
- Нет таймаута и обработки ошибок внешнего AI API: ошибки сети, rate limit и `5xx`
  превращаются в HTTP 500.
- Инструкция и пользовательский ввод склеиваются в одном `user`-сообщении, поэтому
  пользователь может пытаться переопределить инструкции приложения (prompt injection).
- Контекст не сохраняется: модель не может продолжить разговор на основе предыдущих
  реплик.
- Нет ограничения частоты запросов, что создаёт риск исчерпания квоты провайдера.
- Ответ модели вставляется в DOM через `innerHTML` в `app/templates/index.html`; это
  необходимо заменить на безопасное использование `textContent` или на Markdown-рендеринг
  с санитизацией.

## 9. Итог

AI-интеграция представляет собой компактный асинхронный мост между веб-чатом и
`openai/gpt-4o` в GitHub Models API. Она подходит для демонстрации базового сценария
«текстовый запрос — текстовый ответ», но пока не является платформой для сложных
диалогов, RAG или мультиагентных систем. Дальнейшее развитие следует начать с
конфигурируемости провайдера, безопасной передачи инструкций, таймаутов и обработки
ошибок, истории диалогов и потоковой выдачи ответа.
