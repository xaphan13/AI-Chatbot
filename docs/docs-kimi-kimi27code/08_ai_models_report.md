# Отчёт по интеграции приложения с AI-моделями

## 1. Общая сводка

Приложение **AI Chatbot Assistant** интегрировано с LLM (Large Language Model) через [GitHub Models API](https://docs.github.com/en/github-models). В текущей реализации это одиночный stateless-чат: пользователь вводит сообщение в браузере, бэкенд передаёт его выбранной модели и возвращает сгенерированный текст.

Инференс выполняется через официальный Python SDK `openai` (`AsyncOpenAI`), который вызывает OpenAI-совместимый эндпоинт `https://models.github.ai/inference/`. Аутентификация происходит Bearer-токеном — GitHub Personal Access Token (`GITHUB_TOKEN`) с правом `models:read`.

> **Важно:** на момент написания отчёта модель (`openai/gpt-4o`) и базовый URL (`base_url`) [захардкожены](app/services/chat.py) в коде. Смена провайдера или модели требует правки исходников.

---

## 2. Как происходит общение с нейросетями

### 2.1. Протокол и формат запроса

Общение идёт по HTTP(s) через OpenAI-совместимый формат `/chat/completions`:

```json
{
  "model": "openai/gpt-4o",
  "messages": [
    { "role": "user", "content": "Hey ChatGPT, you are a AI chatbot... Here is the prompt: <prompt>" }
  ]
}
```

- **Метод:** `POST`
- **Content-Type:** `application/json`
- **Авторизация:** `Authorization: Bearer <GITHUB_TOKEN>`
- **Endpoint:** `https://models.github.ai/inference/v1/chat/completions` (SDK формирует путь автоматически)

Ответ приходит в виде стандартного `ChatCompletion`:

```json
{
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "Ответ модели..."
      }
    }
  ]
}
```

### 2.2. Архитектура потока данных

```
Браузер (index.html)
  │  POST /api/chat  { prompt: "..." }
  │  Cookie: fastapiusersauth=<jwt>
  ▼
app/api/v1/chat.py — chat_endpoint()
  │  1. Валидация ChatRequest
  │  2. Depends(current_user) → проверка JWT
  ▼
app/services/chat.py — get_chat_response()
  │  1. Конкатенация системного промпта + prompt
  │  2. client.chat.completions.create(...)
  ▼
GitHub Models API (openai/gpt-4o)
  ▼
JSON { response: "..." } → браузер
```

### 2.3. Системный промпт

Системная инструкция вшита прямо в строку в `app/services/chat.py`:

```python
message = (
    "Hey ChatGPT, you are a AI chatbot don not tell your name or any personal information. "
    "Here is the prompt you asked for: " + prompt
)
```

Это не отдельное `system`-сообщение, а префикс к `user`-сообщению. Как следствие:

- нельзя менять поведение бота без изменения кода;
- пользовательский ввод не санитизируется (риск prompt injection);
- нет параметров `temperature`, `max_tokens`, `top_p` и т.д.

## 3. Возможности приложения

| Возможность | Реализовано | Примечание |
|-------------|-------------|------------|
| Текстовый диалог с AI | ✅ Да | `POST /api/chat` возвращает текстовый ответ. |
| Аутентификация перед чатом | ✅ Да | Требуется авторизация через `current_user` (JWT/Cookie). |
| Сохранение истории сообщений | ❌ Нет | Каждый запрос независимый, контекст не передаётся. |
| Потоковая передача (streaming / SSE) | ❌ Нет | Ответ приходит целиком, пользователь ждёт полной генерации. |
| Выбор модели пользователем | ❌ Нет | Модель `openai/gpt-4o` захардкожена. |
| Настройка температуры / параметров | ❌ Нет | Не передаются в запросе. |
| Настраиваемый system prompt | ❌ Нет | Захардкожен в `get_chat_response()`. |
| Мультиагентная система | ❌ Нет | Только один вызов к одной модели. |
| Обработка ошибок LLM API | ❌ Нет | Таймауты, 5xx, rate limit не обрабатываются. |
| WebSocket-чат | ❌ Нет | Только HTTP-запросы. |
| Работа с изображениями / файлами | ❌ Нет | Передаётся только текстовое поле `prompt`. |

## 4. Мультиагентное использование

### 4.1. Текущее состояние

В текущей архитектуре **мультиагентность не реализована**. Вызов идёт строго по схеме «один пользователь → один endpoint → один LLM-вызов → один ответ».

### 4.2. Что понадобится для мультиагентности

Если потребуется реализовать несколько специализированных агентов, типичные подходы:

1. **Несколько ролей в одном запросе**  
   Передавать в `messages` массив с разными `role` и `content`, чтобы модель имитировала диалог агентов.

2. **Каскадные вызовы**  
   Последовательно вызывать LLM: первый агент анализирует запрос, второй формирует ответ, третий проверяет результат. Каждый вызов может использовать разные модели или системные промпты.

3. **Параллельные агенты**  
   Использовать `asyncio.gather()` для одновременного вызова нескольких моделей/агентов и агрегировать ответы.

4. **Orchestrator + Worker агенты**  
   Выделить оркестратор, который решает, какие агенты нужны, и вызывает их. Для этого потребуется расширить схему `ChatRequest` и добавить слой бизнес-логики в `app/services/chat.py`.

> **Вывод:** фундамент для мультиагентности — асинхронный `AsyncOpenAI` и FastAPI — есть, но сама логика отсутствует. Для реализации нужно хранить историю, добавить промежуточные шаги и управление состоянием диалога.

## 5. Какие модели и провайдеры можно использовать

### 5.1. Текущий провайдер

Приложение использует **GitHub Models API**:

```python
base_url = "https://models.github.ai/inference/"
```

### 5.2. Доступные модели через GitHub Models

GitHub Models предоставляет единый OpenAI-совместимый интерфейс к моделям разных вендоров. Точный список зависит от региона, тарифа и даты, но к нему относятся, например, семейства:

- **OpenAI**: `openai/gpt-4o`, `openai/gpt-4o-mini`, `openai/o1`, `openai/o3-mini` и др.
- **Anthropic**: `anthropic/claude-3-5-sonnet`, `anthropic/claude-3-opus` и др.
- **Google**: `google/gemini-1.5-flash`, `google/gemini-1.5-pro` и др.
- **Meta**: `meta/llama-3.3-70b-instruct`, `meta/llama-3.2-11b-vision-instruct` и др.
- **Mistral**: `mistral/mistral-large`, `mistral/mistral-small` и др.
- **Cohere**: `cohere/command-r-plus`, `cohere/command-r` и др.
- **DeepSeek**: `deepseek/deepseek-r1` и др.

> **Примечание:** перечисленные модели — примеры доступных через GitHub Models. Перед использованием проверяйте актуальный каталог в документации GitHub Models.

### 5.3. Переход на других провайдеров

Так как используется SDK `openai`, переход на другой OpenAI-совместимый провайдер сводится к смене `base_url` и `api_key`:

| Провайдер | Пример `base_url` | Токен |
|-----------|-------------------|-------|
| OpenAI | `https://api.openai.com/v1` | `OPENAI_API_KEY` |
| Azure OpenAI | `https://<resource>.openai.azure.com/openai/deployments/<deployment>` | Azure API key |
| GitHub Models | `https://models.github.ai/inference/` | `GITHUB_TOKEN` (models:read) |
| Локальный LLM (Ollama, vLLM, LM Studio) | `http://localhost:11434/v1` | обычно не требуется |
| Anthropic (нативный API) | `https://api.anthropic.com` | требуется SDK `anthropic` | *

\* Для Anthropic лучше использовать официальный SDK `anthropic`, так как его нативный API не полностью совпадает с OpenAI-совместимым форматом, хотя некоторые прокси предоставляют совместимый слой.

## 6. Ограничения и риски

| Риск | Место | Описание |
|------|-------|----------|
| **Захардкоженная модель** | `app/services/chat.py:20` | Для смены модели нужна правка кода. |
| **Prompt injection** | `app/services/chat.py:15-18` | Пользовательский ввод напрямую конкатенируется в промпт. |
| **Нет обработки ошибок** | `app/services/chat.py:19` | Таймауты и сетевые ошибки приводят к HTTP 500. |
| **Нет таймаута** | `app/services/chat.py:19` | Запрос может висеть неограниченно долго. |
| **Нет истории** | `app/services/chat.py` | Модель не помнит предыдущие сообщения в рамках сессии. |
| **XSS в чате** | `app/templates/index.html:225` | Ответ модели вставляется через `innerHTML` без санитизации. |
| **Нет rate limiting** | `app/api/v1/chat.py` | Любой авторизованный пользователь может спамить `/api/chat`, расходуя токены. |
| **Не валидируется `GITHUB_TOKEN`** | `app/core/config.py:13` | Приложение запускается с пустым токеном, но чат падает с 401. |

## 7. Рекомендации по расширению интеграции

1. **Вынести модель и параметры в конфигурацию**  
   Добавить в `app/core/config.py` поля `LLM_MODEL`, `LLM_BASE_URL`, `LLM_TEMPERATURE`, `LLM_MAX_TOKENS`.

2. **Передавать `system` как отдельное сообщение**  
   Использовать `messages=[{"role": "system", "content": ...}, {"role": "user", "content": ...}]`.

3. **Сохранять историю чата**  
   Добавить таблицы `conversation` и `message`, передавать последние N сообщений в запросе.

4. **Добавить обработку ошибок и таймауты**  
   Обернуть `client.chat.completions.create()` в `try/except` с `timeout` и возвращать понятные ошибки клиенту.

5. **Реализовать streaming**  
   Вернуть ответ через `StreamingResponse` (SSE) с `stream=True` в SDK.

6. **Поддержать выбор модели в API**  
   Расширить `ChatRequest` полем `model: str | None`.

7. **Поддержать мультиагентность**  
   Добавить сервис `AgentOrchestrator` и отдельные роли с разными системными промптами.

## 8. Итог

Приложение демонстрирует базовую интеграцию с LLM через GitHub Models API. Для пользователя это простой текстовый чат с одной фиксированной моделью. Архитектурно приложение готово к расширению: асинхронный клиент, dependency injection и FastAPI позволяют легко добавить выбор моделей, историю, streaming и мультиагентные сценарии. Основной следующий шаг — вынести параметры LLM в конфигурацию и добавить обработку ошибок.
