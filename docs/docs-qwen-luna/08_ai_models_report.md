# Отчёт о работе приложения с AI-моделями

## 1. Краткое резюме

Приложение представляет собой веб-чат на FastAPI с серверными Jinja2-шаблонами. AI-запросы выполняются асинхронно через пакет `openai` и OpenAI-совместимый API GitHub Models.

Текущая схема интеграции:

```text
Браузер
  │ POST /api/chat
  │ {"prompt": "..."}
  ▼
FastAPI + аутентификация пользователя
  ▼
app.services.chat.get_chat_response()
  ▼
AsyncOpenAI
  │ base_url = https://models.github.ai/inference/
  │ model = openai/gpt-4o
  ▼
GitHub Models API
  ▼
{"response": "..."}
```

Главный вывод: сейчас это однопользовательский stateless-чат с одной жёстко заданной моделью и одним провайдером. Архитектура допускает расширение, но выбор модели, провайдера, параметры генерации, память диалога и мультиагентность пока не вынесены в конфигурацию или отдельные сервисы.

## 2. Как выполняется запрос к нейронной сети

### Шаг 1. Отправка сообщения из браузера

В `app/templates/index.html` JavaScript получает текст из `<textarea>` и отправляет JSON-запрос:

```http
POST /api/chat
Content-Type: application/json
Cookie: fastapiusersauth=<JWT>

{"prompt":"Объясни async/await в Python"}
```

Интерфейс перед отправкой показывает индикатор набора текста. Ответ не передаётся потоково: браузер ждёт завершения всего HTTP-запроса.

### Шаг 2. Проверка доступа и валидация

`app/api/v1/chat.py` принимает `ChatRequest` с обязательным полем `prompt` и получает текущего пользователя через `Depends(current_user)`. Поэтому `/api/chat` доступен только аутентифицированным пользователям.

При успешной проверке вызывается:

```python
response = await get_chat_response(prompt=prompt.prompt)
```

### Шаг 3. Подготовка сообщения

`app/services/chat.py` добавляет к пользовательскому тексту встроенную инструкцию:

```python
message = (
    "Hey ChatGPT, you are a AI chatbot don not tell your name or any personal information. "
    "Here is the prompt you asked for: " + prompt
)
```

Важно: это не полноценное разделение ролей `system` и `user`. Инструкция и пользовательский текст объединяются в одну строку и передаются как сообщение с ролью `user`.

### Шаг 4. Вызов модели

Клиент создаётся один раз при импорте модуля:

```python
client = AsyncOpenAI(
    api_key=settings.GITHUB_TOKEN,
    base_url="https://models.github.ai/inference/",
)
```

Запрос выполняется так:

```python
response = await client.chat.completions.create(
    model="openai/gpt-4o",
    messages=[{"role": "user", "content": message}],
)
```

Токен берётся из `GITHUB_TOKEN`, который загружается через `pydantic-settings` из `.env` или переменных окружения.

### Шаг 5. Возврат результата

Из ответа выбирается первый вариант:

```python
return response.choices[0].message.content.strip() if response.choices else ""
```

API возвращает:

```json
{"response":"Текст ответа модели"}
```

Фронтенд добавляет результат в окно чата.

## 3. В каком виде происходит общение с нейронными сетями

Сейчас используется протокол HTTP с JSON и интерфейс Chat Completions, совместимый с OpenAI SDK.

Формат входа внутри SDK — список сообщений:

```python
messages = [
    {"role": "user", "content": "Текст запроса"},
]
```

Поддерживаемый в коде формат сообщения — текстовый. Изображения, аудио, файлы, function/tool calling и структурированные ответы явно не реализованы.

Транспортный уровень:

- клиент: `AsyncOpenAI`;
- запрос: асинхронный HTTP через OpenAI SDK;
- endpoint провайдера: `https://models.github.ai/inference/`;
- авторизация: Bearer-токен из `GITHUB_TOKEN`;
- ответ: обычный JSON после полного завершения генерации;
- streaming через `stream=True`, SSE или WebSocket отсутствует.

## 4. Какие возможности предлагает приложение

### Реализовано

- регистрация пользователя;
- вход и выход через Cookie/JWT-аутентификацию;
- защищённая страница чата;
- отправка текстового prompt в AI;
- отображение ответа в браузере;
- индикатор ожидания ответа;
- API-доступ к `/api/chat`;
- альтернативный JWT/Bearer backend, подготовленный FastAPI-Users;
- автоматическая Swagger-документация FastAPI на `/docs`.

### Не реализовано

- сохранение истории диалогов в БД;
- передача предыдущих сообщений в модель;
- отдельные настройки модели для пользователя;
- выбор провайдера и модели через UI или `.env`;
- temperature, max tokens, top_p и другие параметры генерации;
- потоковая генерация;
- загрузка файлов и мультимодальные запросы;
- вызов внешних инструментов и функций;
- RAG/поиск по документам;
- оценка качества и трассировка AI-ответов;
- автоматическая модерация prompt/ответов;
- retry, timeout и специализированная обработка ошибок LLM API.

## 5. Модели и провайдеры

### Используется сейчас

| Компонент | Текущее значение |
|---|---|
| SDK | `openai` (`AsyncOpenAI`) |
| Провайдер | GitHub Models |
| Base URL | `https://models.github.ai/inference/` |
| Модель в коде | `openai/gpt-4o` |
| Ключ | `GITHUB_TOKEN` |
| Формат | OpenAI-compatible Chat Completions |

Название модели и URL захардкожены в `app/services/chat.py`. Поэтому фактическая возможность использовать конкретную модель зависит от каталога и разрешений GitHub Models на момент запуска.

### Потенциально совместимые провайдеры

Поскольку приложение использует `AsyncOpenAI` с настраиваемым `base_url`, похожий адаптер можно сделать для любого провайдера, который предоставляет совместимый Chat Completions API. Например:

- OpenAI;
- Azure OpenAI;
- GitHub Models;
- Together AI;
- Groq;
- OpenRouter;
- локальный сервер Ollama с совместимым endpoint;
- vLLM или другой self-hosted OpenAI-compatible gateway.

Это не означает, что эти провайдеры уже подключены. Для каждого потребуется отдельный ключ, base URL, имя модели и проверка совместимости параметров.

### Что нужно изменить для конфигурируемого провайдера

Минимальный вариант — вынести настройки в `app/core/config.py`:

```python
AI_BASE_URL: str = "https://models.github.ai/inference/"
AI_API_KEY: str = ""
AI_MODEL: str = "openai/gpt-4o"
```

Затем использовать их при создании клиента и вызове модели. Для нескольких провайдеров лучше добавить фабрику клиентов или отдельные реализации общего протокола.

## 6. Возможно ли мультиагентное использование

### Состояние сейчас

Нет. В проекте отсутствуют:

- несколько ролей или специализированных агентов;
- планировщик задач;
- маршрутизация запроса между агентами;
- общий контекст и хранилище состояния агентов;
- обмен сообщениями между агентами;
- механизм согласования или проверки результатов;
- параллельный запуск нескольких AI-задач.

Один вызов `/api/chat` вызывает одну модель один раз и возвращает один текстовый ответ.

### Возможно ли добавить

Да. Текущий слой `app/services/chat.py` можно превратить в адаптер одного AI-провайдера, а поверх него добавить оркестрацию. Пример целевой схемы:

```text
Пользовательский запрос
        ▼
Оркестратор
  ├── агент-аналитик
  ├── агент-разработчик
  ├── агент-поисковик
  └── агент-проверяющий
        ▼
Сбор и проверка результатов
        ▼
Итоговый ответ пользователю
```

Для реализации потребуются как минимум модели данных для задач/сообщений, хранилище состояния, правила маршрутизации и ограничения по времени/стоимости. Для параллельного исполнения можно использовать `asyncio.gather`, но перед внедрением понадобится защита от превышения rate limit провайдера.

## 7. Ограничения и риски текущей AI-интеграции

- `GITHUB_TOKEN` допускает пустое значение конфигурации, поэтому ошибка обнаруживается только при обращении к API.
- Нет явного timeout для запроса к модели.
- Ошибки API не преобразуются в контролируемый ответ; исключение может привести к HTTP 500.
- История не передаётся, поэтому модель не видит предыдущие реплики.
- Пользовательский ввод напрямую конкатенируется с инструкцией, что упрощает prompt injection.
- Имя модели нельзя сменить без изменения исходного кода.
- Ответ приходит целиком, что увеличивает воспринимаемую задержку.
- На фронтенде ответ вставляется через `innerHTML`; текст AI и пользовательский текст необходимо экранировать перед выводом.
- Автоматических тестов для AI-сервиса в проекте нет.

## 8. Итоговая оценка

Приложение уже содержит рабочий минимальный контур общения с AI: аутентифицированный пользователь отправляет текст, FastAPI вызывает GitHub Models через OpenAI-совместимый клиент, а браузер показывает ответ. Это хороший MVP-слой интеграции.

Для полноценной AI-платформы следующими приоритетами являются конфигурирование провайдера и модели, таймауты и обработка ошибок, история сообщений, streaming, безопасный вывод, тестирование и только затем мультиагентная оркестрация.
