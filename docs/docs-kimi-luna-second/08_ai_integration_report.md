# 08 — Отчёт о работе приложения с AI-моделями

## 1. Краткое резюме

`AI Chatbot Assistant` — монолитное асинхронное веб-приложение на FastAPI с серверным рендерингом Jinja2. AI-функция реализована как защищённый HTTP-чат: браузер отправляет текст пользователя на backend, backend вызывает внешний OpenAI-совместимый API, а затем возвращает готовый текстовый ответ.

### Текущий статус

| Возможность | Статус | Комментарий |
|---|---|---|
| Отправка запроса в языковую модель | Реализовано | `app/services/chat.py` вызывает `AsyncOpenAI` |
| Используемый провайдер | Реализовано | GitHub Models API |
| Используемая модель | Реализовано | `openai/gpt-4o` |
| Аутентификация пользователя | Реализовано | Cookie/JWT через FastAPI-Users |
| JSON API чата | Реализовано | `POST /api/chat` |
| История диалога на сервере | Не реализовано | Каждый запрос независим |
| Streaming-ответ | Не реализовано | Ответ приходит целиком |
| Выбор модели пользователем | Не реализовано | Модель захардкожена в сервисе |
| Несколько AI-агентов | Не реализовано | В проекте только один вызов одной модели |
| Инструменты, RAG, загрузка файлов | Не реализовано | В текущем коде отсутствуют |

Важно отличать заявленные возможности от реализованных: приложение уже выполняет базовый AI-чат, но не является многоагентной платформой и не хранит контекст беседы.

## 2. Архитектура AI-интеграции

Поток одного сообщения выглядит так:

```text
Браузер
  │ POST /api/chat
  │ {"prompt": "..."}
  ▼
FastAPI endpoint: app/api/v1/chat.py
  │ проверка cookie/JWT и валидация ChatRequest
  ▼
AI-сервис: app/services/chat.py
  │ AsyncOpenAI.chat.completions.create(...)
  ▼
GitHub Models API
  │ HTTPS + Bearer GITHUB_TOKEN
  ▼
Ответ модели
  │ response.choices[0].message.content
  ▼
Браузер
  │ {"response": "..."}
```

### Основные компоненты

- `app/schemas/chat.py` — входная Pydantic-модель `ChatRequest` с полем `prompt: str`.
- `app/api/v1/chat.py` — защищённый endpoint `POST /api/chat`.
- `app/services/chat.py` — создание клиента `AsyncOpenAI` и вызов модели.
- `app/core/config.py` — получение `GITHUB_TOKEN` из `.env` или переменных окружения.
- `app/templates/index.html` — JavaScript-клиент, который отправляет запрос и отображает ответ.
- `pyproject.toml` — зависимость `openai`, используемая как клиент OpenAI-совместимого API.

## 3. Как выполняется запрос к модели

В текущей реализации сервис создаёт клиент при импорте модуля:

```python
client = AsyncOpenAI(
    api_key=settings.GITHUB_TOKEN,
    base_url="https://models.github.ai/inference/",
)
```

Затем для каждого сообщения выполняется:

```python
response = await client.chat.completions.create(
    model="openai/gpt-4o",
    messages=[{"role": "user", "content": message}],
)
```

Из ответа извлекается содержимое первого варианта:

```python
return response.choices[0].message.content.strip() if response.choices else ""
```

Внутри `message` сначала добавляется фиксированный текст-инструкция, после чего к нему конкатенируется пользовательский ввод. Отдельное сообщение с ролью `system` сейчас не используется.

## 4. Формат общения с нейронной сетью

Общение происходит не напрямую из браузера с моделью, а через backend приложения.

### Запрос браузер → приложение

```http
POST /api/chat HTTP/1.1
Content-Type: application/json
Cookie: fastapiusersauth=<JWT>
```

```json
{
  "prompt": "Объясни принцип работы REST API"
}
```

### Вызов приложения → провайдер

OpenAI SDK преобразует вызов Python в HTTPS-запрос к endpoint провайдера. Логическая структура запроса соответствует Chat Completions API:

```json
{
  "model": "openai/gpt-4o",
  "messages": [
    {
      "role": "user",
      "content": "Инструкция приложения. Объясни принцип работы REST API"
    }
  ]
}
```

Заголовок авторизации формирует SDK на основании `GITHUB_TOKEN`:

```http
Authorization: Bearer <GITHUB_TOKEN>
Content-Type: application/json
```

### Ответ провайдера → приложение

Провайдер возвращает объект с массивом вариантов. Приложение берёт текст из `choices[0].message.content` и формирует собственный ответ:

```json
{
  "response": "REST API — это ..."
}
```

### Роли сообщений

Протокол поддерживает роли `system`, `user` и `assistant`, однако текущий сервис передаёт только одно сообщение с ролью `user`. Поэтому модель не получает предыдущие реплики и не может сохранять контекст между HTTP-запросами.

## 5. Возможности приложения

### Реализованные возможности

1. **Аутентифицированный чат.** Доступ к странице `/chat` и `POST /api/chat` требует текущего пользователя.
2. **Асинхронный вызов AI.** Backend не блокирует event loop синхронным сетевым вызовом: используется `AsyncOpenAI` и `await`.
3. **OpenAI-совместимый протокол.** Провайдер подключён через стандартный интерфейс SDK с заменой `base_url`.
4. **Web-интерфейс.** Пользователь вводит текст в браузере, видит индикатор набора и получает ответ без перезагрузки страницы.
5. **API-доступ.** Сервис можно вызывать не только через UI, но и любым HTTP-клиентом с действующей cookie/JWT-аутентификацией.
6. **Регистрация и вход.** FastAPI-Users управляет пользователями, cookie и JWT, необходимыми для доступа к AI-чату.

### Не реализованные возможности

- долговременная история разговоров;
- передача нескольких предыдущих сообщений в `messages`;
- потоковая генерация токенов через SSE или WebSocket;
- настройка `temperature`, `max_tokens` и system prompt через конфигурацию;
- выбор модели и провайдера через UI или API;
- function calling/tool calling;
- RAG по документам и векторный поиск;
- multimodal-ввод (изображения, аудио, видео);
- фоновые задачи и очереди для долгих AI-операций;
- оценка качества ответов и трассировка AI-вызовов;
- multi-agent orchestration.

## 6. Ограничения и риски текущей реализации

### Контекст и состояние

История в базе данных не сохраняется. SQLite используется для пользователей, но таблиц диалогов и сообщений нет. Каждый запрос содержит только текущий `prompt`.

### Надёжность

В `app/services/chat.py` не заданы timeout и обработчики ошибок API. Сетевой сбой, ошибка авторизации GitHub, rate limit или ошибка сервиса могут привести к необработанному исключению и HTTP 500.

### Конфигурация

`GITHUB_TOKEN` читается из настроек, но модель и `base_url` находятся прямо в коде. Для подключения другого провайдера потребуется менять исходный файл или предварительно вынести эти параметры в конфигурацию.

### Безопасность

- Токен нельзя помещать в Markdown, frontend-код, URL или логи.
- Пользовательский ввод напрямую добавляется в инструкцию модели, поэтому возможны prompt injection-сценарии.
- В `app/templates/index.html` текст ответа вставляется через `innerHTML`; это создаёт XSS-риск, если ответ содержит опасный HTML.
- Значение `SECRET` имеет небезопасный демонстрационный default и должно быть переопределено в окружении.
- Нет rate limiting для AI-запросов, поэтому один пользователь может создавать чрезмерную нагрузку или расходовать лимиты провайдера.

## 7. Рекомендованный порядок развития

1. Вынести `LLM_MODEL`, `LLM_BASE_URL`, `LLM_TIMEOUT`, `LLM_SYSTEM_PROMPT` и параметры генерации в `app/core/config.py`.
2. Добавить timeout и обработку `APIConnectionError`, `APITimeoutError`, `RateLimitError` и других ошибок OpenAI SDK.
3. Заменить `innerHTML` для текста сообщений на безопасное создание DOM-узлов через `textContent`.
4. Добавить модели `Conversation` и `Message`, а затем передавать историю в `messages`.
5. Реализовать streaming через SSE и обновление сообщения по мере поступления фрагментов.
6. Добавить лимиты длины запроса, rate limiting и журналирование без записи секретов и полного содержимого приватных запросов.
7. После появления базового надёжного chat service добавить оркестратор агентов, а не вызывать несколько моделей непосредственно из frontend.

## 8. Вывод

Сейчас приложение представляет собой простой защищённый AI-чат поверх GitHub Models API. Его сильная сторона — небольшая и понятная интеграция с OpenAI-совместимым endpoint. Основные ограничения — отсутствие истории, streaming, конфигурируемости, обработки ошибок и multi-agent-логики. Для расширения не требуется менять весь стек: достаточно выделить конфигурацию и AI-сервис, добавить хранение состояния, а затем построить оркестрацию поверх этих компонентов.
