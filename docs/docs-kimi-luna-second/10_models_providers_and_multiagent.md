# 10 — Модели, провайдеры и multi-agent использование

## 1. Что поддерживается сейчас

В текущем репозитории фактически настроена одна связка:

| Компонент | Текущее значение | Где задано |
|---|---|---|
| SDK | `openai` / `AsyncOpenAI` | `app/services/chat.py`, `pyproject.toml` |
| Провайдер | GitHub Models API | `app/services/chat.py` |
| Base URL | `https://models.github.ai/inference/` | `app/services/chat.py` |
| Модель | `openai/gpt-4o` | `app/services/chat.py` |
| Авторизация | `GITHUB_TOKEN` | `app/core/config.py` |
| API-операция | `chat.completions.create` | `app/services/chat.py` |
| Режим ответа | Один полный JSON-ответ | `app/api/v1/chat.py` |

Следовательно, текущая система не предоставляет пользователю переключатель моделей и не содержит реестра провайдеров. Указание другой модели в запросе клиента сейчас невозможно: endpoint принимает только `prompt`.

> Каталог моделей GitHub Models может меняться. Наличие модели у провайдера нужно проверять в его актуальной документации и настройках доступа, а не считать постоянным свойством приложения.

## 2. Какие модели можно использовать

### В рамках текущего приложения

С гарантией по исходному коду заявлена только модель `openai/gpt-4o`. Она передаётся в `model=` непосредственно из `app/services/chat.py`.

Другие модели GitHub Models могут быть доступны **только после проверки**:

1. модель присутствует в актуальном каталоге GitHub Models;
2. токен пользователя имеет право вызвать её;
3. модель поддерживает используемую операцию `chat.completions`;
4. формат ответа совместим с ожиданием `choices[0].message.content`;
5. лимиты контекста, rate limit и поддерживаемые параметры подходят приложению.

### После параметризации

Если вынести модель в `LLM_MODEL`, можно переключать модели через окружение без изменения кода:

```env
LLM_MODEL=openai/gpt-4o
```

Это будет техническая возможность выбора модели на стороне администратора. Чтобы дать выбор пользователю, потребуются отдельная allowlist-модель, валидация запроса, UI и контроль стоимости/лимитов.

## 3. Какие провайдеры можно подключить

`AsyncOpenAI` умеет обращаться к API, совместимому с используемым OpenAI-протоколом. Поэтому архитектурно возможны следующие варианты:

| Провайдер/тип | Совместимость по подходу | Что потребуется изменить |
|---|---|---|
| GitHub Models | Уже используется | Ничего для текущей конфигурации |
| OpenAI API | Обычно совместим с Chat Completions | `base_url`, API key, название модели и лимиты |
| Azure OpenAI | Совместим концептуально, но имеет особенности URL/API version/deployment | Специальные настройки endpoint, deployment и API version |
| OpenRouter | Предоставляет OpenAI-совместимый интерфейс | `base_url`, ключ и имя модели провайдера |
| Локальный vLLM | Может предоставлять OpenAI-совместимый server | Локальный URL, ключ/режим auth и доступная модель |
| Локальный Ollama | Может использовать OpenAI-совместимый endpoint в зависимости от версии/режима | URL, модель и проверка поддерживаемых операций |
| Другой OpenAI-compatible gateway | Зависит от реализации | URL, auth, модель и проверка ответа |

Эта таблица описывает **архитектурную совместимость**, а не факт, что каждый вариант уже протестирован в данном репозитории. Для каждого провайдера нужно отдельно проверить:

- точный endpoint и способ авторизации;
- поддерживаемую операцию (`chat.completions`, Responses API или другую);
- формат `messages` и ответа;
- streaming и tool calling;
- ограничения контекстного окна и rate limit;
- политику хранения и обработки пользовательских данных;
- стоимость и условия лицензии/доступа.

## 4. Минимальная параметризация провайдера

Рекомендуемый первый шаг — добавить настройки:

```python
class Setting(BaseSettings):
    LLM_API_KEY: str = ""
    LLM_BASE_URL: str = "https://models.github.ai/inference/"
    LLM_MODEL: str = "openai/gpt-4o"
    LLM_TIMEOUT: float = 30.0
```

И использовать их в сервисе:

```python
client = AsyncOpenAI(
    api_key=settings.LLM_API_KEY,
    base_url=settings.LLM_BASE_URL,
    timeout=settings.LLM_TIMEOUT,
)

response = await client.chat.completions.create(
    model=settings.LLM_MODEL,
    messages=[{"role": "user", "content": prompt}],
)
```

Для обратной совместимости можно временно использовать `GITHUB_TOKEN` как значение `LLM_API_KEY`, но лучше перейти к единому нейтральному имени конфигурации после добавления валидации.

## 5. Возможен ли multi-agent режим

### Ответ для текущей версии

Нет. В текущем приложении multi-agent использование не реализовано.

Сейчас есть:

- один AI-сервис;
- один вызов модели на пользовательский запрос;
- одна фиксированная модель;
- один фиксированный system/user prompt;
- отсутствие оркестратора;
- отсутствие маршрутизации задач между ролями;
- отсутствие общего состояния и результатов промежуточных шагов;
- отсутствие SDK или библиотеки для multi-agent orchestration в `pyproject.toml`.

Само наличие OpenAI-совместимого API не делает приложение multi-agent. Для multi-agent нужен дополнительный слой, который решает, какой агент вызывается, в каком порядке, с какими данными и когда остановиться.

## 6. Как может выглядеть multi-agent архитектура

Минимальная схема для этого проекта:

```text
Пользователь
    │
    ▼
POST /api/chat
    │
    ▼
Оркестратор
    │ определяет тип задачи
    ├── Исследователь — собирает факты или контекст
    ├── Программист — анализирует код или формирует решение
    ├── Редактор — проверяет структуру и стиль ответа
    └── Финализатор — объединяет результаты
    │
    ▼
Единый ответ пользователю
```

Агенты могут использовать одну модель с разными system prompt или разные модели/провайдеры. Это два разных сценария:

1. **Ролевые агенты на одной модели.** Дешевле и проще, но агенты не являются независимыми моделями.
2. **Гетерогенная система.** Разные модели выбираются для планирования, поиска, генерации и проверки; выше гибкость, но сложнее конфигурация, стоимость и контроль данных.

## 7. Пример простого последовательного оркестратора

**Это пример будущего расширения, не текущий код приложения.** Он показывает принцип без привязки к конкретному multi-agent-фреймворку:

```python
from dataclasses import dataclass

from openai import AsyncOpenAI

from app.core.config import settings


client = AsyncOpenAI(
    api_key=settings.GITHUB_TOKEN,
    base_url="https://models.github.ai/inference/",
)


@dataclass
class Agent:
    name: str
    system_prompt: str
    model: str


researcher = Agent(
    name="researcher",
    system_prompt="Собери ключевые факты и отдели факты от предположений.",
    model="openai/gpt-4o",
)

reviewer = Agent(
    name="reviewer",
    system_prompt="Проверь точность, полноту и безопасность черновика.",
    model="openai/gpt-4o",
)


async def run_agent(agent: Agent, task: str) -> str:
    response = await client.chat.completions.create(
        model=agent.model,
        messages=[
            {"role": "system", "content": agent.system_prompt},
            {"role": "user", "content": task},
        ],
    )
    return response.choices[0].message.content.strip() if response.choices else ""


async def run_workflow(user_prompt: str) -> str:
    research = await run_agent(researcher, user_prompt)
    review_task = f"Запрос пользователя: {user_prompt}\n\nЧерновик исследователя:\n{research}"
    return await run_agent(reviewer, review_task)
```

Для production такой пример необходимо дополнить ограничением длины промежуточных результатов, timeout на каждый шаг, обработкой ошибок, трассировкой, лимитом числа шагов и защитой от циклических вызовов.

## 8. Изменения, необходимые для полноценного multi-agent режима

### Backend и доменная модель

- выделить интерфейс `LLMProvider` или аналогичный адаптер;
- добавить конфигурацию нескольких моделей и ключей провайдеров;
- создать `Agent` с ролью, system prompt, разрешёнными инструментами и лимитами;
- создать `Workflow`/`Task` для описания последовательности шагов;
- добавить таблицы заданий, шагов и результатов, если workflow должен переживать перезапуск;
- связать каждое задание с пользователем и правами доступа.

### API и UI

- определить endpoint запуска workflow;
- возвращать статусы `queued`, `running`, `completed`, `failed`;
- для длительных задач использовать очередь и фоновые workers;
- добавить streaming статуса или результатов через SSE/WebSocket;
- показывать пользователю не только финальный текст, но и понятный статус выполнения, не раскрывая секретные внутренние данные.

### Безопасность и эксплуатация

- allowlist моделей и инструментов;
- лимит бюджета, токенов, времени и числа шагов;
- изоляция внешних инструментов и сетевых запросов;
- фильтрация prompt injection между агентами;
- аудит вызовов без записи секретов;
- retry только для идемпотентных операций;
- fallback-провайдер при недоступности основного, если это разрешено политикой данных.

## 9. Сравнение возможностей

| Сценарий | Текущая версия | После развития |
|---|---:|---:|
| Один запрос → один ответ | Да | Да |
| Разные модели через env | Нет | Да |
| Выбор модели пользователем | Нет | Возможно, через allowlist |
| Несколько провайдеров | Нет | Да, через provider adapter |
| История сообщений | Нет | Да, через Conversation/Message |
| Несколько агентов | Нет | Да, через orchestrator/workflow |
| Параллельные агенты | Нет | Возможно, через `asyncio.gather` и лимиты |
| Проверка ответа вторым агентом | Нет | Да |
| Streaming промежуточных результатов | Нет | Да, через SSE/WebSocket |

## 10. Итог

Приложение уже умеет работать с языковой моделью через GitHub Models API и OpenAI-совместимый `AsyncOpenAI`. На уровне протокола можно подготовить подключение других провайдеров и моделей, но текущая реализация жёстко фиксирует URL и модель.

Multi-agent режим возможен без полной смены технологического стека, но это отдельный этап разработки. Сначала следует параметризовать provider/model, добавить timeout, обработку ошибок и состояние диалогов. После этого поверх AI-сервиса можно безопасно реализовать оркестратор агентов, лимиты и наблюдаемость.
